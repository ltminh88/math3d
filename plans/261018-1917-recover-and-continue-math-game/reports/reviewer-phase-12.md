## Warning
W1. Boot/hydration race drops writes, and a total store failure loses data with no notice. `enqueue()` returns `false` when `store` is undefined and reports nothing (progress-sync.ts:44-45). `recordQuizQuestion` also returns early (:86). After that, `connectStore` overwrites `gameState.progress` with the snapshot (:63). So a Play, avatar or book-table click before `data-boot=ready` gets reverted: the avatar visibly flips back through renderProgress, and `started` and `table` are lost. Severity is low per click, because the window is the IDB open plus the import, and no XP or answers are realistically at risk. The second half is worse. If `openGameStore` throws a non-blocked error (for example, `loadOrCreateActiveProfile` or `loadSnapshot` fails), store-boot.ts:61 only logs it, `store` stays undefined, and every write for the rest of the session is dropped. No toast fires, and "Lưu tiến trình" shows nothing. Fix: (a) keep #play, #boy/#girl and #import-save-code disabled until `bootStore` finishes, or buffer jobs that arrive before connect and replay them after `connectStore`; (b) in the outer catch, fall back to `openGameStore({ db: createMemoryGameDb() })` and show `ts('notPersistent')`; (c) have `enqueue` call `reportFailure` when there is no store.

W2. A tab never learns that another tab switched the active profile. Repro: tabs A and B boot together on an origin that has a v1 blob. B's `loadOrCreateActiveProfile` runs before A's import transaction, so B holds P1 (empty). A imports and switches the active profile to P2 with the marker. B's import then returns `'already-imported'` (legacy-save-import.ts:130), but B's snapshot stays on P1 (game-store.ts:182). B shows zero progress and commits to P1, and next boot opens P2, so B's answers are orphaned. The risk table claimed "second tab sees marker": it does see the marker, but it keeps the stale profile. The same thing happens with reset or a save-code import in A while B is open: B keeps writing to the old profile. Fix: inside `commitSession`, `acceptLevel` and `updateGameMeta`, read `META_ACTIVE_PROFILE` in the transaction. If it differs from `snapshot.profile.id`, reload the snapshot and reject or rebase (or broadcast through a `BroadcastChannel('math3d')` and call `connectStore` again). As a minimum, on `'already-imported'` reload the snapshot from the active profile.

## Suggestion
S1. One failing batch blocks the queue. `flushProgress` retries `unsent[0]` forever (progress-sync.ts:105-108). A deterministic error (an `InvalidDeltaError` such as a profile mismatch, or a closed DB after versionchange) therefore blocks every later batch for the session. Fix: on `InvalidDeltaError`, drop the batch (log it) instead of keeping it.
S2. Stale Leitner box after a failed commit. A new batch's `getStat` reads the committed snapshot only (progress-sync.ts:90). When batch N is still in `unsent`, a fact repeated in batch N+1 derives box, streak and errs from stale data. Because the box with the newest `seenAt` wins (progress-repository.ts:114), that stale box overwrites. Fix: overlay `unsent[*].delta.facts[key].box` and `local` in `getStat`.
S3. Answers can be lost on tab close. Up to 4 answers and bridge segments depend on an async IDB transaction started in `pagehide`. That is fine on desktop but not guaranteed on iOS Safari. The original wrote synchronously per answer. Consider flushing on every bridge-mode correct answer, since the visible segment is the progress a child notices disappearing.
S4. versionchange loses pending answers. The `blocking()` handler closes the connection immediately (idb-database.ts:69-72), so the `unsent` batch is lost and a misleading "chưa cho phép lưu" toast stacks on the reload dialog. Fix: run `flushProgress().finally(close)`, or suppress `reportFailure` once the reload prompt is open.
S5. A failed legacy import can overwrite later progress. When an import fails (no marker), anything done that session (play, save-code import, reset) gets replaced silently by the retry on the next boot. Fix: write the marker on any `replaceProgress`, or skip the import when the active profile has `sessionCount > 0`.
S6. `decodeSaveCode` can throw a raw `RangeError`. A crafted code with a valid CRC and a huge `seenSec` makes `new Date(x*1000).toISOString()` throw `RangeError` (save-code-compact-json.ts:57), which breaks the "throws SaveCodeError" contract. The UI maps it to 'payload', so nothing crashes. Fix: bound `seenSec` to ≤ 8.64e9 or wrap the call in try/catch and throw `SaveCodeError('payload')`.
S7. Reset no longer resets sound and music. The original `defaultSave()` reset turned sound on and music off; settings now survive a reset (settings-dialog.ts:25). This is probably better, but record it as an intentional deviation from the original.
S8. The read-only WebMCP tool writes. `read_adventure_progress` calls `flushProgress` (progress-tool.ts:23), so a tool marked read-only commits batches. It leaks nothing (counters plus avatarId only), but consider reading snapshot plus pending data instead.

Checked and OK: v1 size cap of 256 KB; save-code cap of 4096 checked before decoding; at most 54 exportable facts (~2.3 KB code); base64url without padding (forgiving atob); pooling of `m7_3`/`m3_7` into `mul:3x7`, which sums counters and takes the max `lastSeenAt` (review sets box 1); box override range 1..5; i18n and the legacy translator both read `appSettings` once; blocked → memory store plus toast; terminated → reload prompt.
